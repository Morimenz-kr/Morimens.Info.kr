# Eremora 기능·UI 조사와 Morimens.Info.kr 비교

조사: 2026-10-05~06 KST. 구현·배포 없이 공개 사이트와 로컬 코드만 조사했다.

## 1. 결론

Eremora의 핵심은 **기록을 읽고, 조건을 좁히고, 실제 빌드를 확인하는 동선**이다. 우리 사이트는 도감·공략·편성·비밀계약 실험 도구가 더 넓다. ScareCrow에는 전투 실험 기능도 있다. 부족한 것은 기능의 수보다 이들을 연결하는 사용자 흐름과 일관된 정보 표현이다.

파티 요약은 데스크톱에서 네 명을 한 화면에 비교할 수 있게 하는 것이 맞다. 현재 ScareCrow의 왼쪽 2×2 카드가 상세 입력 옆에서 계속 따라오는 구조보다, 네 명의 요약을 위에 고정된 문서 영역으로 놓고 상세 편집을 명시적으로 여는 구조를 권한다. **스크롤에 붙는 sticky를 없앤다는 뜻이지, 전체 페이지 스크롤을 금지한다는 뜻은 아니다.**

모바일까지 네 명과 모든 입력을 한 화면에 넣으려 하면 글씨·터치 영역이 망가진다. 작은 화면에서는 2×2 요약 또는 압축 목록과 별도의 편집 화면이 필요하다. Eremora도 모바일 요약은 2×2다.

## 2. 조사 범위와 확실성

- 홈과 6개 상위 메뉴: Profiles, Leaderboards, Meta, Events, Library, About.
- 프로필: 데모와 실제 공개 프로필 1건. 성장·장비 상세, 이미지 공유 옵션, 일반 클리어·PvP UI.
- 도전: D-Zone, Phantasmal Dive, Hectic Skybound Rail의 실제 기록 화면과 공통 전투 분석.
- 랭킹: D-Zone, Phantasmal Dive, Hectic Skybound Rail, Collection 모두 진입 확인.
- 메타: 전체 채용률, 폴룩스 개별 페이지, 포함·제외 검색, 실제 클리어 상세.
- 이벤트: 현재/전체/임무/체험 분류와 펼침 상세. 유물 도감: 검색·필터·변형 상세.
- 확인 방법: 웹 문서 + 브라우저 접근성 트리 + 실제 클릭 + 화면 캡처 + DOM 크기 측정.

아래는 **공개 메뉴에서 발견한 기능 표면의 목록**이다. 모든 플레이어·모든 시즌·418개 유물의 개별 내용까지 전수 검증했다는 뜻은 아니다. 숨겨진 관리자 기능, 서버 내부 구현, 다운로드된 이미지 파일의 품질, 모든 오류 경로는 조사 범위 밖이다. 이미지 저장 버튼은 존재와 옵션을 확인했지만 다운로드 파일 자체는 검증하지 않았다. 실제 프로필의 최근 기록은 비동기 조회 지연이 있었고 해당 UI 구조는 데모에서도 확인했다.

현재 사이트와 옛 변경 기록을 구분했다. 예전에 있던 Collection/Records를 지금의 개인 보유품 도감 기능으로 세지 않았다. 현재 프로필에는 Career/Challenges/Stages/Matches가 보이며, **Collection 랭킹은 별도로 존재한다.**

## 6. UI·UX에서 배울 점

1. **입력하지 않아도 먼저 읽힌다.** 네 명의 레벨·계령·개별 카드 레벨·장비·중요 스탯이 보인다. 지금 ScareCrow 요약은 초상화/이름/레벨/명륜이 중심이라 다른 사람의 성장과 비교하기 어렵다.
2. **비교 기준이 정렬되어 있다.** 동일한 위치에서 같은 지표를 본다. 이미지와 문장 길이가 달라도 수치 행은 같은 역할을 한다.
3. **이미지에 텍스트를 보완한다.** 명륜은 그림만 보여 주지 않고 이름과 단계도 있다. 익숙하지 않은 장비를 알아볼 수 있다.
4. **게임 아이콘은 학습 비용을 줄인다.** 하지만 아이콘만으로 끝내지 않고 이름/도움말/접근성 이름을 붙인다. hover만으로 설명하면 모바일 사용자는 놓친다.
5. **공통 정보는 한 번만 둔다.** 은열쇠와 계정 레벨은 카드마다 반복하지 않는다.
6. **요약과 상세의 역할을 나눈다.** 빌드 전체는 상세, 네 명 비교는 요약, 전투 성적은 별도 분석이다.
7. **의미 있는 상태를 설명한다.** 지원/미해금/기록 없음/표본 적음/갱신 지연을 분리한다.
8. **결과에서 다음 행동으로 이어진다.** 사용률→장비/동료→조합→실전 기록→개별 빌드/코드. 우리에게는 그 다음 `내 편성으로 가져오기→ScareCrow에서 실험`까지 가능하다.
9. **시각적 강조가 절제되어 있다.** 캐릭터/장비 원화가 주인공이고 테두리·배경·보조 글씨가 경쟁하지 않는다. 숫자는 정렬되어 읽힌다.
10. **상위 탐색과 세부 입력을 분리한다.** 기본 필터 먼저, 상세 조건은 More filters. 모든 설정을 처음부터 펼쳐 두지 않는다.

우리 사이트에는 이미 `common.css`, `components.css`, `party_builder.css`의 어두운 표면·황금색 강조·Pretendard·기존 선택 모달이 있다. Eremora의 갈색 배경/영문 장식 서체를 그대로 새 테마로 덮는 것은 권하지 않는다. **정보 구조와 게임 아이콘 표현을 배우고, 색·간격·선택 모달은 우리 기존 것을 재사용한다.** 디자인 참고 지침의 표면 계층·강조색 절제 원칙도 이 판단에만 사용했다. 다른 브랜드의 색/서체를 도입하지 않았다.

Eremora도 그대로 복사하면 안 되는 부분이 있다. 작은 글씨와 두 칼럼 모바일 카드는 320px에서 장비명이 여러 줄이 된다. 성장/카드 숫자열은 이름 설명 없이 보면 불명확하다. 데모의 일부 재능 효과에는 `[Arg1]` 같은 원문 토큰이 남아 있다. 이미지와 요약의 미감이 곧 데이터 정확성이나 접근성 완성도를 보증하지 않는다.

- `party_builder.html:39` — 팀 이름 편집이 클릭 SVG. 이름 있는 button과 키보드 접근 필요.
- `party_builder.html:56` — 은열쇠 선택이 클릭 div. button 의미와 키보드 조작 필요.

이는 이번 조사에서 발견한 항목이며 전체 접근성 감사 완료 선언은 아니다. 코드 수정은 하지 않았다.

※ 비밀계약이 없는 기존 융재금구 편성 도구에는 행을 억지로 추가하지 않는다. ScareCrow/실전 기록에는 필요하다. 은열쇠는 두 도구 모두 파티 공통 항목이다.

- 요약 자체는 스크롤을 따라오지 않는다.
- 초상화 클릭만으로 수정 모드에 들어가게 하지 않는다. `상세 보기`, `각성체 변경`, `설정`의 동작을 구분한다.
- 명륜 I/II를 누르면 기존 명륜 정보 선택 방식으로 연다. 캐릭터 전체 변경을 유발하지 않는다.
- 성장과 개별 카드 레벨을 같은 상세 패널에서 수정하되, 저장된 값은 네 명 요약에 즉시 보인다.
- 최종 능력치 자동 계산/게임값 직접 입력은 구분하고, 직접 입력하면 중복 장비 가산을 막는다.
- 지원 캐릭터·내 캐릭터·실전 가져오기·현재 편성의 출처를 표시한다.
- 파티 설정과 전투 조작을 서로 다른 단계로 구분한다. 전투 중 거대한 편성 카드가 계속 화면을 차지할 필요는 없다.
- 기존 선택 모달/정렬/검색 컴포넌트를 공통으로 사용한다. 문구뿐 아니라 선택 상태·확정 규칙까지 같아야 한다.

## 8. 게임 클라이언트 활용 가능성과 데이터 경계

[Eremora About](https://eremora.com/about)은 게임 안의 공개 플레이어 프로필을 데이터 출처로 명시한다. 사용자가 들은 ‘클라이언트 검색 활용’이라는 설명과 부합한다. 다만 공식 문서에는 통신 프로토콜·인증·수집 구현이 공개되어 있지 않으므로 특정 웹 API를 그대로 호출하면 된다고 단정하지 않는다.

우리도 출발점이 없는 상태는 아니다. `docs/dzone-live-usage-api.md`에 기존 비공개 독립 클라이언트를 재사용해 융재금구 목록/상세를 수집하고, 신규 전투를 중복 제거해 집계하는 운영이 문서화되어 있다. 공개 사이트는 Worker에서 **정제된 집계만** 읽는다.

현재 정책상 원본 응답·UID·리플레이 코드·인증 정보는 공개 API/저장소에 저장하지 않는다. 따라서 플레이어별 기록이나 코드를 공개하는 기능은 기존 통계를 단순히 더 예쁘게 그리는 작업이 아니다. **공개 범위/비식별화/조회 제한/보관 기간을 별도로 결정하고 API를 확장해야 한다.** 이 조사에서는 로그인·게임 조회 실행·새 수집·외부 게시를 하지 않았다.

| 원하는 기능 | 필요한 데이터 | 현재 판단 |
|---|---|---|
| 게임 아이콘 요약 | 스탯 ID→원본 아이콘→한국어명 | 로컬 추출 자산을 검증해 연결. Eremora CDN을 의존 자산으로 복사하지 않음 |
| 장비·성장별 통계 | 기록 시점의 두 명륜/계령/재능/카드/비밀계약 | 현재 공개 집계 스키마에는 부족. 원본 상세 필드 보존 여부 점검 필요 |
| 보유/성장 맞춤 검색 | 위 필드 + 포함/제외 + 지원 여부 | 기존 보유 목록과 연결 가능하지만 조회 인덱스/API 필요 |
| 실전 빌드 가져오기 | 기록 시점 스탯·장비 옵션·공통 성장·은열쇠 | 단순 캐릭터 목록 복사로는 정확한 재현 불가 |
| 턴별 분석 | 전투별/턴별 피해·치유·방어막·원천 | 상세 기록 제공 범위와 귀속 규칙부터 확인 |
| UID 프로필 | 공개 프로필 조회·오류/갱신 정책 | 기존 클라이언트의 실제 검색 스키마 확인 필요 |
| 이미지 공유 | 이미 보유한 편성 모델 | 신규 게임 조회 없이도 가능. 이름/UID 숨김 옵션 권장 |

클리어 기록은 현재 계정 성장과 다를 수 있다. 정확한 시뮬레이션에는 시작 상태·유물·스테이지 효과·카드/상태·난수도 필요하다. 빌드만 가져왔다고 동일 피해 재현을 보장하지 않는다. 치명타 확률/피해 표시와 실제 카드의 치명타 발생 표시를 둘 다 유지해야 한다.

## 9. 우선순위와 반응형 검토

| 순서 | 내용 | 이유 |
|---|---|---|
| P0 | 파티 요약 4열·sticky 해제·정보 순서 통일 | 지금의 비교/편집 불편을 바로 해소 |
| P0 | 개별 카드 레벨·두 명륜 돌파·성장/스탯 요약 | 설정 기능이 있어도 값이 안 보이면 비교할 수 없음 |
| P0 | 기존 선택 UI와 공통 아이콘/문구 재사용 | 같은 사이트에서 조작을 다시 배우지 않도록 |
| P1 | 이미지 공유·직접 링크·편성 모델 연결 | 데이터 수집 확대 없이도 가치가 큼 |
| P1 | 조건별 실전 검색·기록→내 편성 | 기존 통계와 편성 도구를 연결 |
| P2 | 장비/성장 통계·개인 프로필·전투 분석 | 데이터 스키마/공개 정책/API 확장이 필요 |

Eremora의 동일 Team build를 320/390/768/1024/1280px, 높이 800px에서 측정했다.

| 폭 | 배치 | 카드 폭 대략 | 문서 가로 넘침 |
|---|---|---|---|
| 320 | 2×2 | 135px | 없음 |
| 390 | 2×2 | 170px | 없음 |
| 768 | 2×2 | 347px | 없음 |
| 1024 | 4열 | 230px | 없음 |
| 1280 | 4열 | 288px | 없음 |

390/1280px는 화면 캡처로도 확인했다. 모바일에서는 명륜 I/II가 세로로 놓이고 카드 숫자열이 줄바꿈된다. 네 명을 모바일 한 화면에 강제로 맞추는 구조가 아니다. 이 조사에서 200% 텍스트 확대·모든 중간 분기점·전체 페이지/모달의 키보드/가로모드까지 검증하지 않았으므로 완전한 반응형 적합성 인증은 하지 않는다. 구현 시에는 저장소의 `docs/responsive-design.md` 전체 완료 조건을 별도로 통과해야 한다.
